# Friction log — lane scaffold

## 20:21 (repo 3, interchart) fetch_inbox
What I did: Called fetch_inbox at the start of each repo, as the protocol requires.
What I expected: Either an empty inbox, or new messages since the last fetch (something like a per-agent read cursor), plus release-negotiation requests addressed to me specifically.
What happened (verbatim): The same 6 broadcast "commit" messages come back every time, unchanged, with `"next_cursor":""` each call. None of them are addressed to me individually as a release request — they are commit broadcasts to a large `to` list that includes my agent id among a dozen others. There is no evident way to acknowledge/dismiss a message or advance a cursor, so every repo's inbox check re-reads the same growing backlog of other lanes' commit notifications. This is not itself a blocker, but it means "check inbox for release requests" in practice means "re-scan an ever-growing list of irrelevant commit broadcasts for the rare release request," which doesn't scale — by repo 57 this could be dozens of stale messages per call.
